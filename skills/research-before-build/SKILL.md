# Research Before Build（先调研后构建）

目的：动手之前先回答一个问题——**人类是否已经解决过这个问题？** 重新发明轮子是最大的浪费；社区方案是经过实战检验的压缩经验。但调研本身也有成本，因此本技能只服务探索性任务（方案未定、领域陌生、需要选型/集成/排因），并按未知程度分级检索、以决策影响为验收。

## 第一步：任务定性（必做，成本最低）

本技能只服务探索性任务。加载后先做一道门槛检查，再定检索深度：

**门槛**：路径已明确的执行类工作（用户已指定做法、项目内既有模式可直接套用、本地即可定位的修改）不属于本技能的管辖范围——直接执行，不检索。只有方案未定、领域陌生、需要选型/集成/排因的任务才继续往下走。

| 级别 | 探索特征 | 检索范围 |
|---|---|---|
| **L1** | 已知领域缺细节：技术栈熟悉，缺的是具体 API/配置/参数 | 本地检索优先（项目内实现、依赖清单、已装 skills），必要时 1–2 次定向外部搜索 |
| **L2** | 陌生方案或高风险：选库/选框架、跨系统集成、部署、迁移、云配置、晦涩报错、性能疑难、安全 | **强制外部检索** |
| **L3** | 研究型：文献综述、方案设计、架构选型、开题 | 先例调研**是任务本体的一部分**，系统性多源调研 |

拿不准时按高一级处理。用户明确要求跳过调研时，遵从用户。

## 第二步：按级别检索

### L1 — 本地优先

1. 项目内已有实现、依赖清单、README/AGENTS.md、历史提交
2. 已安装的 skills 中是否有直接对应的能力
3. 仅当本地无果且涉及不熟悉的库/框架时，再做 1–2 次**定向**外部搜索

### L2 — 强制外部检索（按信任从高到低）

1. **官方文档 / 官方 SDK / 厂商最佳实践** —— 最高信任
2. **成熟开源库**（维护活跃、社区规模大、近期有 release、有安全审计）
3. **GitHub issues / discussions**（优先有维护者回复的）
4. **高票 Stack Overflow**（必须检查时效性与版本匹配）
5. **个人博客 / AI 生成内容** —— 最低信任，仅作线索，不作依据

每次搜索前先构造 query：**技术栈 + 版本 + 症状 + 约束**。禁止泛搜。

### L3 — 系统性调研

在 L2 基础上扩展：学术论文、行业白皮书、内部知识库（Zotero/笔记/wiki）、多个独立来源交叉验证。

## 第三步：候选评估（决策影响）

对每个候选方案回答四个问题：

- **相关度**：解决的是同一问题，还是只是表面相似？
- **信任度**：来源属于哪一级？是否经过实战检验？
- **时效性**：与当前版本/环境是否兼容？是否仍在维护？
- **迁移成本**：适配到当前约束需要多少改动？有无许可证/安全问题？

## 第四步：输出先例备忘（L2/L3 必须，L1 可省略）

```
## 先例备忘
- 检索范围：官方文档 X、repo Y、issue Z（列出实际查过的来源）
- 候选：A / B / C
- 评估：A 兼容当前版本 ✓；B 已废弃 ✗；C 许可证冲突 ✗
- 决策：采纳 A 并改造（理由）；
  或"均不适用，自行实现（已查 X/Y/Z，均不满足约束 N）"
```

**没有决策影响的调研是纯开销。** 如果检索结果不改变任何做法，只需一句话说明，不要写长备忘。

## 止损与防退化

- 连续 2 轮检索无有效结果 → 停止检索，转入执行，注明"已检索未找到先例"
- 禁止为检索而检索：每次搜索前明确"这个结果会如何改变我的做法"
- **搜不到 ≠ 不存在**：声称"无先例"时，必须列出实际查过的地方
- 采纳社区方案后必须验证：版本兼容、测试通过、license 检查、必要时安全扫描

## 结果沉淀

同类型任务的调研结论（来源链接 + 结论 + 适用条件）记入笔记或知识库，下次直接复用，避免重复搜索。
